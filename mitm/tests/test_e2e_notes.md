# Layer-2 TLS wallet-injection — E2E notes

Manual end-to-end record for the Layer-2 interceptor (mitmproxy addon that
injects the read-only wallet provider into cold third-party HTTPS tabs).
This is the Task 6 deliverable: there is no automated test for the full
cross-process path, so every step below is recorded honestly as either
PROVEN at the HTTP layer on this Mac, or NOT YET EXERCISED (deferred to an
on-device / on-VLAN test with a real GUI browser).

## Topology used for the local run (Mac)

Local E2E uses mitmproxy in `--mode regular` (an explicit HTTPS proxy),
NOT `--mode transparent`. Transparent mode + the portal's iptables :443
REDIRECT is the on-VLAN device path; it cannot be exercised on a single
Mac with no second device behind the gateway. Regular mode drives the
exact same addon and the same proxy routes, so it proves the
injection/strip/forward logic; only the packet-interception front door
differs.

- Proxy (Flask, Task 4 routes): ran on 127.0.0.1:8091 with
  `ENSCA_DB=/tmp/ensca_e2e/ensca.db` and
  `WALLET_CA_PATH=~/.mitmproxy/mitmproxy-ca-cert.pem`.
  (Port 8091, not the default 8081, because a stale orphan proxy from
  prior work held 8081 and lacked the Task 4 routes — left untouched.)
- mitmdump listener: 127.0.0.1:8443, from the DEDICATED mitm venv
  (`mitm/.venv`), with
  `WALLET_L2_PROVIDER_URL=http://127.0.0.1:8091/wallet/provider.l2.js`.
- CA: `~/.mitmproxy/mitmproxy-ca-cert.pem`, bootstrapped by running
  mitmdump once. Trusted by passing `--cacert` to curl (stands in for the
  device installing it via `/wallet/setup`).
- `provider.l2.js`: regenerated by `gen_provider.py` targeting base
  `http://127.0.0.1:8091`; served 200 by the proxy.

## Steps

### 1. CA route — PROVEN
`GET http://127.0.0.1:8091/wallet/ca.crt` → 200, `x-x509-ca-cert`
attachment. `GET /wallet/secrets.env` → 404 (allowlist holds; no
traversal / arbitrary read).

### 2. provider.l2.js served + absolute URLs — PROVEN
`GET /wallet/provider.l2.js` → 200. All three fetches are rewritten from
relative to absolute at the configured base:
- `http://127.0.0.1:8091/api/wallet/account`
- `http://127.0.0.1:8091/api/wallet/rpc`
- `http://127.0.0.1:8091/wallet/read-methods.json`
This is what lets the script work when injected into a foreign origin
(a relative fetch would hit the dapp's own host and 404).

### 3. Injection into a MITM-able dapp — PROVEN (HTTP layer)
`curl --cacert <ca> -x http://127.0.0.1:8443 https://app.uniswap.org/`
→ HTML comes back with exactly ONE
`<script src="http://127.0.0.1:8091/wallet/provider.l2.js"></script>`
spliced into `<head>`, and the CSP / CSP-Report-Only / X-Frame-Options
response headers stripped. So the browser that loaded this HTML WOULD
fetch and run the provider.

### 4. HSTS-preloaded dapp passthrough — PROVEN
`curl --cacert <ca> -x http://127.0.0.1:8443 https://aave.com/`
→ 0 provider tags (untouched); the host is in the addon/run_mitm
ignore list. A system-trust-only curl (no `--cacert`) to aave through
the proxy returned 200, confirming the real upstream cert is served
(genuine passthrough, not a broken intercept). aave.com is HSTS-preloaded
and cannot be intercepted on a stock browser — this is expected and
documented, not a bug.

### 5. Read-only wallet API path with a DUMMY session — PROVEN (HTTP layer)
Seeded a DUMMY active session in `/tmp/ensca_e2e/ensca.db` for source IP
`127.0.0.1`: group `g_dummy`, user `u_dummy`, session `s_dummy`,
`wallet_address = 0x000000000000000000000000000000000000dEaD`
(a standard burn/test address — NOT any real key), `ens_name dummy.eth`,
active (logged_out_at / revoked_at NULL). Then, through the proxy the
injected script talks to:
- `GET /api/wallet/account` → 200
  `{"address":"0x…dEaD","name":"dummy.eth"}`. (Before seeding: 404
  `no_account` with a valid-but-empty DB, or 500 against a DB whose schema
  was never initialized — the earlier 500 was purely `no such table:
  sessions`, i.e. uninitialized DB, not an endpoint bug.)
- `POST /api/wallet/rpc` `eth_getBalance` → the request is accepted by the
  read-method allowlist and FORWARDED to the real Sepolia RPC. On this Mac
  the upstream itself was unreachable (network egress), so the response was
  a clean JSON-RPC upstream-error object, NOT a proxy crash — the forward
  path is proven; upstream reachability is an environment condition, not
  code. On a host with egress this returns the real balance.
- `POST /api/wallet/rpc` `personal_sign` → `-32601`
  `"method not permitted (read-only)"`. The write/sign path is refused —
  the read-only guarantee holds at the proxy.

## NOT YET EXERCISED (deferred to on-device / on-VLAN GUI test)

The following require a real GUI browser and/or a second device behind the
gateway, and were NOT run here. Do not read the PROVEN steps above as
covering them:

- **Real browser EIP-6963 announce + connect modal.** The injected
  `provider.js` announcing `eip6963:announceProvider` and a dapp's
  connect-wallet modal listing it, then a click-through connect, was
  exercised only at the HTTP layer (the script is present and its
  endpoints resolve). It was NOT clicked through in a real browser with
  devtools. This is the main remaining GUI gap.
- **`--mode transparent` + portal iptables :443 REDIRECT.** The on-VLAN
  front door (device → gateway :443 → mitmdump :8443, no per-app proxy
  config) was not run — needs a second device on the VLAN. Local run used
  `--mode regular` instead.
- **Device trust of the CA via `/wallet/setup`.** Locally the CA was
  trusted by curl `--cacert`; a real phone/laptop installing the profile
  from the setup page was not exercised.
- **Live balance from a reachable Sepolia RPC.** The forward path is
  proven; an actual on-chain balance value depends on upstream egress that
  this Mac lacked.

## Deferred / flagged (repo hygiene, not blockers)

- `web/public/wallet/provider.l2.js` is a generated artifact and is not
  gitignored — it is regenerated by `gen_provider.py` on each launch.
  During this session it once transiently vanished from disk (200 → 404 →
  regenerated → stable 200); the generator does not delete it, so this
  looked like a transient/race, not a code defect. Consider gitignoring
  the generated variant.
- mitmproxy MUST run from its own venv (`mitm/.venv`), never the shared
  proxy venv: mitmproxy 9.x hard-pins flask<2.3, incompatible with the
  proxy's flask 3. The addon imports only the dependency-free
  `proxy/csp_headers.py`, so the mitm process never loads flask/requests.
  The VM deploy must provision this second venv.
